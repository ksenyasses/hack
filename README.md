# KITCHEN OPERATIONS

Система учёта продуктов, контроля сроков годности и стоп-листа в ресторане.
Хакатон FLAGMAN, команда из двух человек.

---

## Реализованная функциональность

### Сроки годности и партии

- Приёмка поставок: срок годности вводится **с упаковки** и не рассчитывается — повар переносит то, что видит на коробке;
- склад ведётся **по партиям**, у каждой свой номер поставки, количество и дата прихода;
- для каждой партии считается статус: сколько дней осталось, «скоро истекает» (до 3 дней) или просрочена;
- просроченные партии автоматически попадают в очередь на списание и в горячие предложения с пометкой «не продаём»;
- остатки в **технологической карте** блюда считаются в порциях, а не в килограммах.

### Списание по FEFO

- при заказе порции списываются **по принципу FEFO** — сначала та партия, у которой раньше истекает срок;
- на кухне повар видит, из какой именно партии брать продукт: номер поставки, дату срока и количество;
- списание идёт **в одной транзакции**: если не хватило хотя бы одного ингредиента, откатывается весь заказ — остатки не списываются частично;
- перед транзакцией выполняется предварительная проверка, чтобы вместо ошибки показать понятное сообщение;
- внутри транзакции проверка повторяется — это защита от двойного расхода при параллельных заказах.

### Стоп-лист

- блюдо уходит в стоп-лист автоматически, если закончился **любой** ингредиент или истёк срок хотя бы одной нужной партии;
- причины формулируются по-разному: «продукт закончился», «срок истёк», «не хватает на все порции» — видно, что именно делать;
- блюдо можно остановить вручную, даже если продукты есть;
- стоп-лист сразу виден официанту в меню — заказать нельзя.

### Горячие предложения

- система сама предлагает, какие блюда готовить и подавать, пока продукты свежие;
- приоритет считается: чем меньше дней до срока у продукта и чем больше порций он закрывает, тем выше;
- по каждому предложению объясняется причина — «Креветки: срок истекает сегодня, остаток 1,80 кг — хватит на 45 порций»;
- промо-блюдо дня всегда показывается первым в меню официанта.

### Заказы

- три роли: **управляющий**, **повар**, **официант** — интерфейс у каждого свой;
- официант выбирает стол или режим «навынос», выбирает режим подачи — всё сразу или по мере готовности;
- кухня обновляется в реальном времени и показывает заказ по позициям;
- повар отмечает позицию готовой — в архив уходит имя повара;
- официант жмёт «Выдан», и заказ уходит в архив — там видно время, стол, состав, кто готовил и кто выдавал;
- заказ можно отменить, товар вернётся на склад;
- архив фильтруется по датам, столу и сотруднику.

### Списание

- у просроченного продукта система сама предлагает создать заявку на списание;
- заявку создаёт повар, **подтверждает управляющий** — списание происходит только после подтверждения;
- есть история заявок с указанием, кто запрашивал, кто подтвердил и почему.

### Прогноз и закупка

- по каждому продукту видно, на сколько дней хватит остатка при текущем темпе заказов;
- система подсказывает, **что и сколько заказать**, если остаток упал ниже минимума;
- видно, какой именно продукт ограничивает блюдо;
- если по блюду ещё не было продаж, система так и говорит — «За период не продавалось,
  прогноз построить нельзя», а не выдаёт выдуманное число.

### Учёт и журнал

- каждое движение продукта записывается: приход, списание по заказу, списание в пустоту, возврат;
- в журнале видно, кто и когда двигал остаток;
- есть аналитика списаний.

## Основной стек технологий

**Backend:** C# / .NET 10, ASP.NET Core, Entity Framework Core 10, Npgsql, JWT Bearer, BCrypt, Swagger.

**База данных:** PostgreSQL 16, миграции EF Core.

**Frontend:** React 19, TypeScript 6, Vite 8, axios. Стили — собственные CSS-переменные, без UI-кита.

**Инфраструктура:** Docker, Docker Compose, Git.

**Авторизация:** три роли на уровне контроллеров, токен в localStorage, пароли хранятся в виде BCrypt-хешей.

## Установка и запуск

### 1. База данных

В корневой директории проекта:

```bash
docker compose up -d
```

Поднимает PostgreSQL на порту **5433** — не 5432, потому что на 5432 может работать
системный PostgreSQL. Дальше контейнер стартует автоматически вместе с Docker.

### 2. Загрузить демо-данные

Без этого шага база будет пустой: миграции создадут только таблицы и трёх
пользователей, а блюд и продуктов не будет.

```bash
node scripts/seed.mjs
```

Скрипт ходит в API по адресу из переменной окружения `API_URL`
(по умолчанию `http://localhost:5071/api`) и создаёт 51 продукт, две поставки
и 10 блюд с технологическими картами. Запускать **после** старта бэкенда и на пустой базе.

**Заказы скрипт по умолчанию не создаёт.** Кухня и архив остаются пустыми, а журнал
показывает только приход. Так система открывается с полным каталогом, но с чистой
историей — можно самому оформить заказ, отметить позицию готовой, выдать заказ и
посмотреть, как он попал в архив и как списались партии.

Чтобы получить наполненную демонстрацию — 7 заказов, из них 5 в архиве:

```bash
node scripts/seed.mjs --orders
```

Специально не привозятся **морепродукты** — из-за них «Ризотто с морепродуктами»
уходит в стоп-лист, чтобы список был не пустым.

Если нужно заполнить базу совсем минимально и без скрипта:

```bash
curl -X POST "http://localhost:5071/api/generate?deliveries=5&orders=8"
```

Это создаёт простой набор из трёх продуктов и двух блюд — годится для проверки
работы, но для демо лучше полный сид.

### 3. Бэкенд

```bash
cd backend/Flagman.Api
dotnet run
```

При старте применяются миграции и, если база пустая, заводятся три пользователя.
Swagger доступен на http://127.0.0.1:5071/swagger

### 4. Фронтенд

Во втором терминале:

```bash
cd frontend
npm install
npm run dev
```

Приложение откроется на http://127.0.0.1:5173

## Конфигурация

Всё читается из переменных окружения, ничего менять в коде не нужно.

### Фронтенд — `frontend/src/config.ts`

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `VITE_API_URL` | `http://localhost:5071/api` | Адрес бэкенда |
| `VITE_USE_MOCK` | не задана | Если `true` — работа на заглушке, без сервера |

Чтобы гонять фронт на заглушках, создайте `frontend/.env.local`:

```
VITE_USE_MOCK=true
```

Файл в `.gitignore`, в репозиторий не попадает. Адрес бэкенда можно задать
относительным (`/api`) — тогда фронт работает на любом хостинге без правок,
нужно только настроить проксирование `/api` на бэкенд. Локально это делает
`vite.config.ts`.

### Backend — `appsettings.json`

| Ключ | Переменная окружения |
|---|---|
| `ConnectionStrings:Default` | `ConnectionStrings__Default` |
| `Jwt:Key` | `Jwt__Key` |
| `Cors:Origins` | `Cors__Origins` — домен фронта через запятую, локальные адреса разрешены всегда |

Двойное подчёркивание — стандартный способ ASP.NET Core прочитать ключ с двоеточием.

```
Models/         сущности и перечисления
Migrations/     миграции EF Core
```

## Полезные команды

Посмотреть таблицы:

```bash
docker exec -it flagman-db psql -U postgres -d flagman -c "\dt"
```

Сбросить базу полностью — данные удалятся:

```bash
docker compose down -v
docker compose up -d
```

После сброса перезапустить бэкенд — он сам применит миграции и заведёт
трёх пользователей, затем пройти шаг 2, чтобы залить демо-данные.

Собрать фронтенд для production:

```bash
cd frontend
npm run build
```
